# JobPilot 项目规划

> 本文用于对齐 JobPilot 的简历目标、当前实现状态和下一阶段开发任务。原则是：**简历不降级，代码向简历追齐**
> ；但开发顺序必须围绕核心业务闭环，不把额度、VIP、AI 扣费、复杂 RBAC、微服务拆分等旁支纳入本轮。

## 1. 项目定位

JobPilot 是一个招聘岗位情报与求职准备平台，核心不是投递管理，也不是重 AI 产品，而是通过真实后端工程能力支撑下面这条闭环：

```text
Scrapy 爬虫采集岗位
  -> Celery + RabbitMQ 投递岗位导入任务
  -> Worker 消费任务并写入 RawJobRecord
  -> 字段规范化、fingerprint 去重、JobPost upsert
  -> 技能抽取与 JobPostSkill 同步
  -> 用户设置目标岗位并维护 UserSkill
  -> 基于 skill_id + level 计算 matched / weak / missing
  -> 根据技能缺口生成学习任务和题目练习
  -> 作答后更新任务进度和用户技能评级
```

项目要展示的后端能力：

- **认证鉴权**：JWT Access Token、Refresh Token、UserSession、设备会话、token 失效。
- **数据建模**：岗位、技能、收藏、目标岗位、用户技能、题库、学习任务等业务模型。
- **复杂查询**：岗位搜索筛选、关联技能加载、用户维度隔离、分页。
- **异步任务**：RabbitMQ + Celery 解耦爬虫采集和岗位导入。
- **幂等处理**：RawJobRecord 输入幂等、JobPost fingerprint 业务幂等、任务重放。
- **学习闭环**：技能差距分析、学习任务生成、作答进度、技能评级更新。
- **工程质量**：Alembic、pytest、ruff、pyright、Docker Compose、可演示脚本。

## 3. API 文档

### 3.1 全局约定

- API 前缀：`/api/v1`
- 交互文档：`http://127.0.0.1:8000/docs`
- 健康检查：`GET /api/v1/health`
- 就绪检查：`GET /api/v1/health/readiness`
- 用户私有资源必须通过当前登录用户解析 `user_id`，禁止由客户端传入用户归属。
- 分页优先使用项目已有 `PageParams` / `PageResult[T]` 约定：服务端多取一条判断 `has_next`，MVP 阶段 `total=None` 可以接受。

## 4. P0 任务拆解

### 4.1 P0-1：UserSession 会话管理

目标：

```text
Access Token + Refresh Token + UserSession
Refresh Token Rotation
Access Token Blacklist
多设备会话管理
```

关键表：

```text
user_sessions
-------------
id
user_id
session_jti
current_refresh_jti
refresh_token_hash
device_id
device_name
user_agent
ip_address
status
revoked_at
revoked_reason
expires_at
last_used_at
created_at
updated_at
```

推荐约束与索引：

```text
UNIQUE(session_jti)
UNIQUE(current_refresh_jti)
INDEX(user_id, status, expires_at)
INDEX(user_id, created_at DESC)
```

任务清单：

- [ ] 新增 `user_sessions` ORM 模型和 Alembic 迁移。
- [ ] 登录时创建 active session，并保存 `session_jti`、`current_refresh_jti`、`refresh_token_hash`。
- [ ] Access Token / Refresh Token payload 增加 `session_jti` 和 `jti`。
- [ ] Refresh 接口基于 session 校验并轮换 refresh token。
- [ ] 支持 logout 当前设备。
- [ ] 支持 logout-all 全部设备。
- [ ] 支持 session list 和踢掉指定设备。
- [ ] Access token blacklist 写入 Redis，TTL 使用 access token 剩余有效期。
- [ ] 用户禁用后拒绝已有 token 继续访问业务接口。

验收标准：

- [ ] 旧 refresh token 不能重复使用。
- [ ] 并发 refresh 最多一个成功。
- [ ] logout 后当前 access token 立即失效。
- [ ] logout-all 后所有设备都不可刷新。
- [ ] 被踢掉的 session 不能继续访问业务接口。
- [ ] 禁用用户即使持有未过期 token，也不能访问业务接口。

测试重点：

```text
test_login_creates_user_session
test_refresh_rotates_refresh_token
test_old_refresh_token_cannot_be_reused
test_concurrent_refresh_only_one_success
test_logout_revokes_current_session_and_blacklists_access_token
test_logout_all_revokes_all_sessions
test_disabled_user_cannot_use_existing_token
```

### 4.4 P0-4：技能匹配与学习任务闭环

技能匹配必须基于结构化字段，不直接依赖 JD 文本或大模型自由生成：

```text
JobPostSkill: skill_id, required_level, importance
UserSkill:    skill_id, proficiency_level, mastery_score
```

匹配规则：

```text
用户没有 skill_id -> missing
用户有 skill_id，但 proficiency_level < required_level -> weak
用户有 skill_id，且 proficiency_level >= required_level -> matched
```

任务清单：

- [ ] 岗位导入后自动同步 `JobPostSkill`。
- [ ] 技能抽取结果映射到标准 `skill_id`。
- [ ] 统一 `required_level` 和 `proficiency_level` 的匹配规则。
- [ ] 根据目标岗位输出 matched / weak / missing。
- [ ] 学习任务生成只处理 weak / missing 技能。
- [ ] 学习任务使用 `source_key` 防重复生成。
- [ ] 作答后按 skill 聚合结果更新 `mastery_score`。
- [ ] `mastery_score` 映射更新 `proficiency_level`。

学习任务生成规则：

```text
1. 读取目标岗位技能缺口。
2. 按 importance、level_gap、岗位优先级排序。
3. 选择 Top K 个 weak / missing 技能。
4. 从题库中筛选 skill_id 匹配、active、approved、难度合适的题目。
5. 创建 study_task、study_task_snapshot、study_task_questions。
6. 题目不足时记录 skipped_reason，不强行生成空任务。
```

幂等 key：

```text
source_key = user_id + target_id + sorted(skill_ids) + task_type + rule_version
```

用户技能评级更新规则：

```text
correct      -> mastery_score 增加，按题目难度加权
wrong        -> mastery_score 小幅减少，避免一次错误大幅降级
skip         -> 不参与评级，只影响任务进度展示
minimum_n    -> 某个 skill 下非跳过题目数量达到阈值后才更新
clamp        -> 单次任务最大变化幅度有限制
mapping      -> mastery_score 映射到 proficiency_level 1~5
```

## 5. 技术注意事项

### 5.1 会话与 token

- `user_sessions` 是长期可信状态，Redis 只做缓存和快速失效补丁。
- `Access Token` 和 `Refresh Token` 都必须携带 `session_jti`。
- `Refresh Token` 明文不落库，只保存 HMAC hash。
- refresh 必须校验 token 类型、签名、过期时间、session active、`current_refresh_jti` 匹配、hash 匹配。
- refresh token rotation 必须是原子操作，避免多标签页并发刷新产生多个有效 refresh token。
- logout 当前设备时撤销当前 session，并把当前 access token 的 `jti` 写入 Redis blacklist。
- 用户禁用、删除或封禁时，不能只依赖 JWT 自身有效期，必须检查用户和 session 状态。

### 5.2 Worker 与异步任务

- RabbitMQ 是 broker，Celery 是任务执行框架，Redis 可作为 result backend 和缓存。
- 重要任务使用 `acks_late`，业务成功后才 ack。
- 任务按“至少一次消费”设计，不能假设消息只执行一次。
- 业务幂等依赖数据库唯一约束、状态字段和 upsert，不依赖应用层先查再插。
- 可恢复失败进入 retry，不可恢复失败进入 failed / dead / DLQ。
- 失败记录必须包含 `message_id`、`raw_record_id`、`error_code`、`error_message`、`retry_count`、`next_retry_at`。
- Worker 日志要记录 `task_name`、`message_id`、`raw_record_id`、`job_post_id`、`status`、`retry_count`。

### 5.3 导入幂等

后端导入分两层幂等：

1. **输入幂等**：`message_id` 或 `source_id + raw_content_hash`，对应 RawJobRecord。
2. **业务幂等**：岗位规范化字段生成 `fingerprint`，对应 JobPost upsert。

fingerprint 只使用相对稳定字段：

```text
company_name_normalized
title_normalized
location_normalized
source_platform / source_job_id 可作为强标识补充
```

薪资、描述、状态、更新时间属于可变字段，不建议进入核心 fingerprint。

禁止写法：

```text
先查 RawJobRecord 是否存在，再 insert。
先查 JobPost fingerprint 是否存在，再 insert。
```

推荐写法：

```text
唯一约束 + on_conflict_do_update / do_nothing
状态机 + CAS 抢占
失败状态可重放
```

### 5.4 代码组织

- 新增 `.py` 文件以 `from __future__ import annotations` 开头。
- 函数和类属性写具体类型注释，尽量不要使用 `Any`。
- service 异常尽量统一到 `src/job_pilot/core/exceptions.py`。
- service 调用 repository 使用显式注入 + factory，不在 service 内部直接 new 具体仓储。
- business repository / service 不直接实例化具体搜索后端；搜索后端从 `build_job_pilot()` 等资源装配入口注入。
- 路由只做 HTTP 模型和内部 contract 映射，业务逻辑放在 service/application。
- 事务边界归 UoW 管，不在 router 中散落 commit/rollback。
- 中文注释保持简短，日志输出使用英文。
- 本地地址统一使用 `127.0.0.1`，避免 Windows + Docker 地址解析问题。
- 读取和写入中文文档时使用 UTF-8。
