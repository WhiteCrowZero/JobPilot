# JobPilot 开发规范

> 适用范围：JobPilot 当前 MVP 迭代期。目标不是写成生产级大而全规范，而是把已经沉淀下来的工程约定固定下来，避免后续阶段反复返工。

## 1. 项目开发原则

JobPilot 是一个 Python FastAPI 后端工程项目，核心目标是通过“岗位情报 → 技能分析 →
学习准备”的业务闭环，展示后端基本功：认证鉴权、数据建模、复杂查询、用户数据隔离、缓存、异步任务、幂等、测试、迁移和部署。

当前仍处于 MVP / 学习型项目阶段，原则是：

1. **先保证业务闭环正确，再做生产级增强。**
2. **当前阶段可以不考虑兼容。** 发现接口、表结构、枚举、索引设计不合理，可以直接重构，不要背历史包袱。
3. **避免过度设计。** 不提前引入 Kafka、Kubernetes、复杂 RBAC、微服务、完整审计系统等。
4. **每个阶段同时产出代码、测试、文档。** 代码解决功能，测试约束核心业务流程，文档用于复盘和面试表达。

## 2. 分层与模块规范

每个业务模块尽量保持下面的结构：

```text
models.py       # SQLAlchemy ORM 与表约束
schemas.py      # HTTP 请求/响应 DTO
contracts.py    # service/application 层使用的查询对象、命令对象
enums.py        # 模块内枚举
exceptions.py   # 模块异常
repository.py   # 数据库查询和写入
service.py      # 业务规则、事务边界、状态流转
router.py       # HTTP 路由和依赖注入
```

基本约定：

1. `router` 只做 HTTP 参数接收、鉴权依赖、调用 application/service，不写业务规则。
2. `service` 负责业务判断、状态流转、事务语义、异常抛出。
3. `repository` 负责 SQL 查询和持久化，不决定复杂业务语义。
4. 用户私有数据必须在查询条件中绑定 `user_id`。
5. 子资源操作必须同时校验父资源归属，例如 `task_question_id` 必须属于当前 `task_id`，而 `task_id` 必须属于当前用户。

代码风格：

1. 每个 `.py` 文件开头使用 `from __future__ import annotations`。
2. 函数参数和返回值写清楚类型，尽量避免 `Any`。
3. 注释和文档用中文，日志内容用英文。
4. 本地地址统一写 `127.0.0.1`，不要写 `localhost`。
5. 文件读写统一使用 UTF-8。

## 3. 查询参数与归档状态规范

状态查询要统一，不要在同一个接口中同时出现 `statuses` 和 `include_archived`。

推荐标准：

| 模块                   | 对外查询参数        | 默认查询范围               |
|----------------------|---------------|----------------------|
| `job_posts`          | `statuses`    | `open`               |
| `job_targets`        | `statuses`    | `active + paused`    |
| `user_skills`        | `statuses`    | `active`             |
| `study_tasks`        | `statuses`    | `todo + in_progress` |
| `job_collections`    | 不提供 status 查询 | `active`             |
| `collection_folders` | 不提供 status 查询 | `active`             |
| `knowledge`          | 不提供 status 查询 | `active`             |
| `questions`          | 不提供 status 查询 | `active + approved`  |

判断标准：

1. **业务状态需要用户主动筛选时，用 `statuses`。** 例如目标岗位、学习任务、岗位状态。
2. **普通用户不该看到的归档/删除数据，不提供查询参数。** 例如知识点、题库的 archived/draft/rejected。
3. **软删除痕迹默认不返回。** `deleted_at` 通常只给内部排查或管理端。
4. **客户端永远只能看到一种状态时，response 中也可以不返回 status。** 避免前端误以为可以操作这些状态。

## 4. Schema 参数校验规范

Schema 校验的目标不是限制一切，而是防止明显无意义、危险或会破坏业务流程的请求进入 service。

重点规则：

1. 列表参数必须限制长度，例如 `skill_ids`、`question_ids`、`statuses` 通常不超过 50。
2. 字符串字段必须限制长度，例如标题 160/200，备注 500/1000，描述 1000/2000，关键词 100。
3. 数字字段必须限制范围，例如掌握等级、优先级、分数、数量、时长。
4. 日期字段要校验基本关系，例如 `due_date >= planned_start_date`。
5. 客户端不能写派生字段，例如学习进度、正确数、错误数、得分、完成百分比。
6. 对作答类请求，要校验“二选一”“不重复”“不能空”等基本规则；题型相关校验放在 service 中读取题目后完成。

不建议把所有业务规则都塞进 Pydantic schema。需要查数据库才能判断的规则，放到 service/repository。

## 5. 数据库索引与约束规范

索引依据只看真实使用路径：`WHERE`、`JOIN`、`ORDER BY`、`UNIQUE/幂等约束`、后台摄入更新路径。字段只是被 `SELECT` 或 `UPDATE`
，不代表需要索引。

### 5.1 必须优先保证的约束

1. 主键、外键。
2. 登录唯一标识，例如 email。
3. 岗位 fingerprint/hash 去重。
4. 恢复型 upsert 依赖的唯一约束。
5. 后台摄入幂等依赖的唯一约束。
6. nullable 字段参与唯一约束时，优先使用 partial unique index，避免 PostgreSQL 中多个 NULL 绕过唯一约束。

典型问题：

```text
UniqueConstraint(a, b, nullable_col)
```

如果 `nullable_col` 可空，普通唯一约束无法阻止多个 `(a, b, NULL)`。应拆成：

```text
(a, b) WHERE nullable_col IS NULL
(a, b, nullable_col) WHERE nullable_col IS NOT NULL
```

### 5.2 联合索引顺序

一般规则：

1. 等值过滤字段在前。
2. 范围/排序字段在后。
3. 用户私有表通常 `user_id` 在最前。
4. 分页排序尽量带稳定 tie-breaker，例如 `id DESC`。
5. 不要给低选择性字段单独建索引，例如单列 `status`、`is_active`、`deleted_at`。

### 5.3 不要过度建索引

1. 多条件筛选不是每个字段都建单列索引。
2. 某个排序功能存在，不代表一定要为该排序建索引。
3. `ILIKE '%keyword%'` 对普通 B-tree 基本无效，不要提前乱加文本索引。
4. 如果未来引入 PostgreSQL FTS、pg_trgm 或 ES，再单独设计搜索索引。
5. MVP 数据量较小时，优先保留核心路径索引，删除无调用路径的提前优化索引。

索引 review 时要明确：这个索引服务哪个查询、是高频用户路径还是后台路径、是否被其他联合索引覆盖、是否增加写入成本。

## 6. Upsert 与写入模式规范

不要为了统一而把所有写入都包装成同一种 upsert。按业务语义区分：

| 类型         | 场景                          | 推荐写法                                  |
|------------|-----------------------------|---------------------------------------|
| 恢复型 upsert | 收藏、目标岗位、用户技能等软删除/归档后恢复      | 使用统一恢复型 helper                        |
| 摄入型 upsert | raw 岗位、岗位主数据、fingerprint 去重 | 使用 PostgreSQL `on_conflict_do_update` |
| 字典/关系去重插入  | 技能字典、题目关系、知识点关系             | 可手写，也可后续抽 `insert_or_ignore`          |
| 普通 create  | 冲突就是业务错误                    | 直接 insert，捕获 IntegrityError 或提前校验     |

核心原则：

1. 恢复型 upsert 必须恢复旧记录，而不是新增重复记录。
2. 摄入型 upsert 要围绕外部数据幂等、fingerprint、raw payload 和错误记录设计。
3. 不要让 repository 用 `None` 表达多种失败原因；失败原因应由明确异常表达。

## 7. 日志规范

日志要服务排查，不追求多。普通查询、DTO 转换、简单参数处理不需要大量日志。

### 7.1 日志分层

| 层                         | 日志策略                             |
|---------------------------|----------------------------------|
| router                    | 尽量不写业务日志，请求日志交给 middleware 或框架层  |
| service                   | 记录关键业务事件，例如创建、归档、作答、生成任务、恢复记录    |
| repository                | 少写日志，只在复杂 upsert、数据库异常、摄入分支中必要记录 |
| middleware/global handler | 统一记录请求异常、耗时、状态码、request_id       |

### 7.2 日志等级

| 等级        | 使用场景                                 |
|-----------|--------------------------------------|
| DEBUG     | 本地调试、低频细节，默认不依赖它排查业务问题               |
| INFO      | 正常关键业务事件，例如任务生成、作答提交、收藏恢复            |
| WARNING   | 可恢复但需要关注的问题，例如跳过无可用题目的技能、重复请求、非法状态流转 |
| ERROR     | 非预期失败，但程序还能继续运行                      |
| EXCEPTION | 捕获异常并需要堆栈时使用                         |

### 7.3 日志内容

推荐记录：

```text
module / event / user_id / resource_id / status / count / reason
```

不要记录：

```text
password / token / 完整请求体 / 自由文本备注 / 答案正文 / 大 payload / 原始 HTML
```

事件命名建议：

```text
auth.login_succeeded
job_collections.collection_upserted
job_targets.target_created
user_skills.skill_upserted
study_tasks.task_generated
study_tasks.attempt_submitted
ingestion.job_post_upserted
```

## 8. 测试规范

测试不追求覆盖率数字，而是覆盖核心业务流程，防止业务状态出乱子。

### 8.1 测试分层

| 类型          | 重点                                              |
|-------------|-------------------------------------------------|
| unit        | 纯函数、schema validator、判分逻辑、分页工具、树构建、策略函数         |
| integration | service + repository + DB，验证事务、软删除、幂等、用户隔离、状态流转 |
| api         | 鉴权、HTTP 参数校验、路由契约、错误码、422/401/404/409           |
| smoke       | 本地真实服务启动后的冒烟检查，默认跳过                             |

### 8.2 必测业务重点

1. 用户只能操作自己的资源。
2. 软删除/归档后默认不可见，但需要恢复的场景能恢复。
3. 恢复型 upsert 不产生重复记录。
4. 生成学习任务要幂等复用，不重复生成同一 source_key 任务。
5. 提交作答要在同一事务内创建 attempt、更新题目状态、更新 progress。
6. 任务完成/归档后不能继续作答或跳过。
7. 错误请求不能产生部分写入。
8. 并发或重复请求不会破坏唯一约束和业务计数。
9. archived/deleted/draft/rejected 数据不会出现在普通用户查询中。
10. 查询参数边界必须稳定，例如超长列表、非法日期、非法状态应被拒绝。

### 8.3 测试写法

1. 使用 AAA：Arrange / Act / Assert。
2. 测试名说明业务行为，例如 `test_submit_attempt_updates_progress_atomically`。
3. 不固定死无关字段，例如具体时间戳、排序细节、自动生成 ID。
4. 重点断言业务不变量，例如计数、状态、用户隔离、是否新增记录。
5. 对错误流程，要断言“没有产生副作用”。

## 9. 文档维护规范

每个阶段至少维护三类文档：

1. `README.md`：面向项目整体说明和运行入口。
2. `docs/当前项目状态.md`：说明当前已经完成什么、下一步是什么。
3. 专项报告：例如索引审查、日志与测试、阶段复盘、接口规划。

文档不要追求越多越好。每份文档必须回答一个明确问题：

```text
这个阶段做了什么？
当前约定是什么？
后续开发要注意什么？
```
