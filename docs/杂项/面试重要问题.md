### Depends 是什么时候执行的？

请求进入路由函数前，FastAPI 会解析依赖树并按顺序执行依赖。如果依赖抛异常，路由函数不会执行。

### 为什么不要在 Mixin 里默认加索引？

Mixin 不知道每张表的真实查询模式。默认单列索引虽然方便，但容易和组合索引重复，导致写入、更新、删除时维护更多
B-tree。用户私有表通常都会带 `user_id`，但真正高效的索引一般还需要状态、排序字段或业务外键一起参与。

### Facade 和 Service 有什么区别？

service 承载具体业务规则，通常按领域模块拆分。facade 面向调用方提供更稳定的公开入口，隐藏 session、cache、service
组装和跨模块调用细节。测试公开 facade 可以减少对内部 service 结构的耦合。

### UoW 解决了什么问题？

Unit of Work 把一组业务操作放进同一个事务边界。service 不需要关心何时提交、失败时如何回滚，调用方也不需要知道 repository
的细节。这样 HTTP、worker、脚本和测试都可以复用同一套公开入口，并获得一致的事务行为。

### 幂等写入模式

唯一约束兜底
PostgreSQL ON CONFLICT 做 upsert
业务层不依赖先查再插保证幂等

### 杂乱梳理（重点内容）

auth token 的处理
数据导入流程处理
默认收藏夹/岗位主目标的更新删除处理（全局唯一并且必须存在，有且只有一个）
软删除处理（upsert和唯一约束兜底）

更新字段覆盖问题（不能无脑全量更新，可能出现None覆盖有效字段）
区分请求、响应字段的None和0（或者空字符串''等等）的区别

### 为什么业务日志不直接用 INFO？

`INFO` 容易同时承载系统生命周期、HTTP access、业务状态变化，排查时会变成大杂烩。业务事件单独放到 `APP`
后，可以直接回答“业务发生了什么”，也方便后续构建业务看板或缓存热度统计。

JobPilot 将日志按语义拆成三类：

1. `APP`：记录业务事件，例如登录失败、注册被拒、摄入幂等跳过、业务校验失败。
2. `INFO`：记录系统生命周期和基础运行信息，例如应用启动、应用关闭、HTTP access、worker ping。
3. `ERROR`：记录错误，例如未捕获异常、服务端错误响应、缓存载荷损坏。

### HTTP 4xx 应该算 ERROR 吗？

通常不算。很多 4xx 是用户输入、权限或业务规则导致的可预期结果，作为基础 access 信息进入 `INFO` 即可。5xx 由异常处理链路记录到
`ERROR`。

### 为什么保留结构化 JSONL？

JSONL 便于后续接入日志平台、按字段过滤和统计，例如按 `event`、`request_id`、`status_code`、`error_code` 查询，不依赖纯文本搜索。

### `flush` 和 `commit` 区别？

`flush` 把变更发送到数据库并获得主键，方便继续写入依赖记录；`commit` 才真正提交整个事务。脚本中同一批数据在一个事务内完成，失败时可以回滚。
