### Depends 是什么时候执行的？

请求进入路由函数前，FastAPI 会解析依赖树并按顺序执行依赖。如果依赖抛异常，路由函数不会执行。

### 为什么不要在 Mixin 里默认加索引？

Mixin 不知道每张表的真实查询模式。默认单列索引虽然方便，但容易和组合索引重复，导致写入、更新、删除时维护更多
B-tree。用户私有表通常都会带 `user_id`，但真正高效的索引一般还需要状态、排序字段或业务外键一起参与。

### Facade 和 Service 有什么区别？

service 承载具体业务规则，通常按领域模块拆分。facade 面向调用方提供更稳定的公开入口，隐藏 session、cache、service
组装和跨模块调用细节。测试公开 facade 可以减少对内部 service 结构的耦合。

### UoW 解决了什么问题？

Unit of Work 把一组业务操作放进同一个事务边界。service 不需要关心何时提交、失败时如何回滚，调用方也不需要知道 repository
的细节。这样 HTTP、worker、脚本和测试都可以复用同一套公开入口，并获得一致的事务行为。

### 幂等写入模式

唯一约束兜底
PostgreSQL ON CONFLICT 做 upsert
业务层不依赖先查再插保证幂等

### 杂乱梳理（重点内容）

auth token 的处理
数据导入流程处理
默认收藏夹/岗位主目标的更新删除处理（全局唯一并且必须存在，有且只有一个）
软删除处理（upsert和唯一约束兜底）
数据流梳理和业务闭环
更新字段覆盖问题（不能无脑全量更新，可能出现None覆盖有效字段）
区分请求、响应字段的None和0（或者空字符串''等等）的区别

### 为什么业务日志不直接用 INFO？

`INFO` 容易同时承载系统生命周期、HTTP access、业务状态变化，排查时会变成大杂烩。业务事件单独放到 `APP`
后，可以直接回答“业务发生了什么”，也方便后续构建业务看板或缓存热度统计。

JobPilot 将日志按语义拆成三类：

1. `APP`：记录业务事件，例如登录失败、注册被拒、摄入幂等跳过、业务校验失败。
2. `INFO`：记录系统生命周期和基础运行信息，例如应用启动、应用关闭、HTTP access、worker ping。
3. `ERROR`：记录错误，例如未捕获异常、服务端错误响应、缓存载荷损坏。

### HTTP 4xx 应该算 ERROR 吗？

通常不算。很多 4xx 是用户输入、权限或业务规则导致的可预期结果，作为基础 access 信息进入 `INFO` 即可。5xx 由异常处理链路记录到
`ERROR`。

### 为什么保留结构化 JSONL？

JSONL 便于后续接入日志平台、按字段过滤和统计，例如按 `event`、`request_id`、`status_code`、`error_code` 查询，不依赖纯文本搜索。

### `flush` 和 `commit` 区别？

`flush` 把变更发送到数据库并获得主键，方便继续写入依赖记录；`commit` 才真正提交整个事务。脚本中同一批数据在一个事务内完成，失败时可以回滚。

### 警惕复用代码式的 mixin 组合拆分

表面优雅，本质问题是： Python mixin 在这里是“组织错觉”

因为：
mixin 不是 domain boundary
只是代码复用工具
会导致依赖隐藏

### 区分归档字段名称使用

如果这个状态会成为用户主动筛选、分 tab、恢复、统计的业务对象，用 statuses；如果只是“默认隐藏的历史数据”，且用户最多点一个“显示归档”，用
include_archived；如果普通用户根本不该看到，就不要暴露查询参数。

- 业务状态 = statuses
- 隐藏开关 = include_archived
- 后台管理 = admin 接口，不放普通客户端

## Search 查询抽象

### 1. 为什么排序必须做白名单映射

用户传入的排序参数不能直接拼成数据库字段名，否则会带来 SQL 注入风险和不可控查询计划。白名单映射把“外部 API 参数”和“内部
SQLAlchemy 排序表达式”隔离开，非法 sort key 应该直接报错，而不是静默降级。

### 2. 为什么列表查询先分页 ID 再加载实体

复杂搜索通常会包含 join、exists、全文匹配和多条件过滤。先在轻量 ID 查询里完成过滤、排序、分页，再按 ID
批量加载列表需要的实体，可以避免列表页加载详情冷字段，也能保持分页结果稳定。

### 3. 为什么需要保序返回

`WHERE id IN (...)` 不保证返回顺序等于传入 ID 顺序。分页 ID 已经包含正确排序，所以二次加载实体后必须按 ID
列表重新排序，否则分页顺序可能被数据库执行计划打乱。

## 知识点树查询与递归 CTE

### 核心结构（去掉业务条件）

```sql
WITH RECURSIVE tree AS (
    -- 1. 根节点
    SELECT *
    FROM knowledge_points
    WHERE parent_id IS NULL

    UNION ALL

    -- 2. 递归子节点
    SELECT child.*
    FROM knowledge_points child
             JOIN tree parent ON child.parent_id = parent.id)

-- 3. 输出
SELECT *
FROM tree;
```

起点部分决定查哪棵树，递归部分通过 `child.parent_id = parent_tree.id` 一层层向下展开。最终 SQL 返回的是扁平行，service 再用
`id -> node` 字典把它组装成嵌套树。

### 1. 常见树模型有哪些？

常见有邻接表、路径枚举、闭包表、嵌套集合。

JobPilot 当前使用邻接表，也就是每个节点保存 `parent_id`。优点是写入、移动节点简单，表结构直观；缺点是查询整棵树需要递归查询或多次查询。

### 2. 为什么这里用递归 CTE？

递归 CTE 可以在数据库内一次性展开整棵子树，避免应用层循环查询导致 N+1。对于 PostgreSQL，`WITH RECURSIVE` 是处理邻接表树结构的常见方案。
ORM relationship 递归加载容易产生 N+1 查询，也很难控制深度、状态过滤和排序。这里用 SQL 一次取全量扁平结果，再在 service 中组装
DTO，边界更清晰。

### 3. 树有什么坑？

分页不能简单对所有扁平节点分页，否则一页里可能只有半棵树。当前实现是先取完整树，再按 `skill_id` 分组后的树响应分页，保证返回项是完整树。
业务层应禁止把节点移动到自己的后代下面。数据库层可以进一步用触发器、闭包表或在 CTE 中维护路径数组防止环。当前 MVP
主要实现读取链路，后续做节点移动时必须补环检测。

## QuestionDetail

### QuestionDetail 查询为什么难

题目详情难点不在主表查询，而在一条题目后面挂了三组一对多关系：

- `Question.options`：选择题选项。
- `Question.answers`：开放题/短答题答案。
- `Question.skill_links`：题目和技能、知识点的关联。

其中 `skill_links` 又继续关联：

- `QuestionSkill.skill`：标准技能名称。
- `QuestionSkill.knowledge_point`：知识点标题。

所以 detail 查询分成两步理解：

1. 先查到这一条 `Question`。
2. 再把页面需要展示的关联集合一次性预加载出来。

代码上使用 `selectinload`：

```python
stmt = (
    select(Question)
    .where(
        Question.id == question_id,
        Question.status == QuestionStatus.ACTIVE,
        Question.review_status == QuestionReviewStatus.APPROVED,
    )
    .options(
        selectinload(Question.options),
        selectinload(Question.answers),
        selectinload(Question.skill_links).selectinload(QuestionSkill.skill),
        selectinload(Question.skill_links).selectinload(QuestionSkill.knowledge_point),
    )
)
```

这里容易写错的是：

```python
selectinload(Question.options).selectinload(QuestionOption)
```

这种写法不对。`selectinload()` 接收的是 ORM relationship 属性，不是模型类。`Question.options` 已经是从题目到选项的
relationship，选项后面没有继续要加载的 relationship，所以只写 `selectinload(Question.options)`。

`Question.skill_links` 后面还要继续拿技能和知识点，所以才写成链式：

```python
selectinload(Question.skill_links).selectinload(QuestionSkill.skill)
selectinload(Question.skill_links).selectinload(QuestionSkill.knowledge_point)
```

### QuestionDetail 映射怎么写

repository 只负责拿 ORM 实体，不负责决定响应结构。service 负责把 ORM 转成 Pydantic response。

题目详情可以先复用列表项映射：

```python
list_item = self._to_list_item(question)
return QuestionDetailResponse(
    **list_item.model_dump(),
    status=question.status,
    review_status=question.review_status,
    source_note=question.source_note,
    created_by_user_id=question.created_by_user_id,
    options=[...],
    answers=[...],
    skills=[...],
)
```

这样不会重复写 `id/title/question_text/question_type/difficulty/source_type/primary_skill/created_at/updated_at`。

三个关联集合分别映射：

```python
options = [
    self._to_option_response(option)
    for option in sorted(question.options, key=lambda option: (option.sort_order, option.id))
]
```

选项展示顺序只看 `sort_order`，再用 `id` 做稳定兜底。

```python
answers = [
    self._to_answer_response(answer)
    for answer in sorted(
        (answer for answer in question.answers if answer.status is QuestionAnswerStatus.ACTIVE),
        key=self._answer_sort_key,
    )
]
```

答案只展示 active，排序规则是官方答案优先，然后新答案优先。这个规则来自产品语义：“官方答案唯一、默认置顶”。

```python
skills = [
    self._to_skill_link_response(skill_link)
    for skill_link in sorted(question.skill_links, key=self._skill_link_sort_key)
]
```

技能关联先展示 primary，再展示 related。因为一个题目可能既考主技能，也顺带涉及相关技能。

## 1. PostgreSQL nullable unique 的坑

nullable 外键参与唯一约束的问题

### 问题现象

原来的 `KnowledgePoint` 使用普通唯一约束：

```python
UniqueConstraint("skill_id", "parent_id", "title")
```

设计意图是：同一个技能下，同一个父节点的知识点标题不能重复。

但 `parent_id` 是可空字段。PostgreSQL 的普通 unique constraint 允许多行 `NULL`，所以根节点场景下：

```text
skill_id = Python
parent_id = NULL
title = Python 基础
```

可以重复插入多条。

### 为什么这是后端常见坑

很多人以为 `UNIQUE(a, b, c)` 会让三列组合严格唯一，但 SQL 里 `NULL` 表示未知值，不等于另一个 `NULL`。因此：

```text
(1, NULL, "A")
(1, NULL, "A")
```

在 PostgreSQL 普通 unique constraint 下不冲突。

### 本次修复

把一个普通唯一约束拆成两个 partial unique index：

```python
Index(
    "uq_knowledge_points_root_title",
    "skill_id",
    "title",
    unique=True,
    postgresql_where=text("parent_id IS NULL"),
)

Index(
    "uq_knowledge_points_child_title",
    "skill_id",
    "parent_id",
    "title",
    unique=True,
    postgresql_where=text("parent_id IS NOT NULL"),
)
```

语义变成：

- 根节点：同一 `skill_id + title` 唯一。
- 子节点：同一 `skill_id + parent_id + title` 唯一。

### 面试怎么讲

可以这样回答：

```text
我遇到过 PostgreSQL nullable unique 的问题。普通 unique constraint 对 NULL 不按相等处理，
所以像知识点树这种 parent_id 可空的邻接表，如果直接对 skill_id、parent_id、title 做唯一约束，
根节点会绕过唯一性检查。

我的处理方式是拆成两个 partial unique index：
parent_id IS NULL 时约束 skill_id + title；
parent_id IS NOT NULL 时约束 skill_id + parent_id + title。
这样数据库层能准确表达业务唯一性，而不是只依赖 service 校验。
```

## 面试官可能追问

### Q1：为什么不直接把 `parent_id` 设为 0？

不建议。`parent_id` 是自关联外键，根节点没有父节点，用 `NULL` 表达最自然。用 0 需要伪造一条不存在的父节点，反而破坏关系语义。正确做法是保留
`NULL`，用 partial unique index 处理唯一性。

### Q2：partial unique index 和 unique constraint 有什么区别？

unique constraint 是全表范围的唯一约束。partial unique index 只约束满足某个条件的行，例如：

```sql
WHERE parent_id IS NULL
```

它适合表达“不同状态/不同空值场景下唯一规则不同”的业务约束。
