# JobPilot 当前项目状态

> 更新时间：2026-07-05。
> 本文按 `README.md` 最新开发方向和当前 `src/`、`tests/`、`deploy/` 代码校准，用于区分“已经有代码证据的能力”和“下一阶段目标”。

## 1. 项目定位

JobPilot 是一个 FastAPI 后端工程项目，围绕招聘岗位数据建立：

```text
岗位情报 -> 技能分析 -> 学习准备
```

当前代码已经具备的主线是：

```text
RawJobRecord 摄入 service
  -> 岗位字段规范化
  -> JobPost fingerprint 去重/upsert
  -> 岗位列表、详情、筛选项
  -> JobPostSkill 技能关系同步 service
  -> 用户收藏、目标岗位、UserSkill 技能画像
  -> 基于 skill_id + proficiency_level 的 matched / weak / missing 分析
  -> 根据目标岗位 missing/weak 技能生成 StudyTask
  -> 作答或跳过后更新任务题目状态和任务进度
```

当前还没有真正跑通的主线是：

```text
爬虫采集
  -> RabbitMQ 投递
  -> Celery Worker 消费岗位消息
  -> 自动执行 raw 摄入、岗位 upsert、JobPostSkill 同步
  -> 作答结果反向更新 UserSkill 评级
```

项目重点展示：认证鉴权、用户数据隔离、岗位摄入幂等、结构化建模、复杂查询、缓存、事务边界、测试和 Docker 基础设施。会话管理、异步消费链路和爬虫联调仍是下一阶段重点。

| Docker 部署 | Compose 有 PostgreSQL、测试库、Redis、pgAdmin、Prometheus、Grafana；没有 RabbitMQ、API、Worker 服务。 | 基础设施部分完成 |

## 6. 已沉淀的工程规范

### 6.1 查询与归档状态

当前已经明确：

| 模块 | 对外查询参数 | 默认查询范围 |
|------|--------------|--------------|
| `job_posts` | `statuses` | `open` |
| `job_targets` | `statuses` | `active + paused` |
| `user_skills` | `statuses` | `active` |
| `study_tasks` | `statuses` | `todo + in_progress` |
| `job_collections` | 不提供 status 查询 | `active` |
| `collection_folders` | 不提供 status 查询 | `active` |
| `knowledge` | 不提供 status 查询 | `active` |
| `questions` | 不提供 status 查询 | `active + approved` |

普通用户默认看不到 archived、removed、deleted、draft、rejected 数据。

### 6.2 分页与搜索

当前列表 API 主要使用共享分页契约：`PageParams` / `PageResult[T]`、查询 `page_size + 1`、service 侧计算 `has_next`，MVP 下 `total=None`。搜索后端通过 `SearchBackend` 显式注入，当前默认实现是 `SqlLikeSearchBackend`，不是 Elasticsearch。

### 6.3 幂等与恢复型写入

已落地的幂等/恢复规则：

1. Raw 摄入通过 `message_id` 和 `source_id + raw_content_hash` 防重复消费。
2. 岗位主数据通过 fingerprint 做 upsert。
3. 学习任务生成通过 `source_key` 复用当前未完成任务。
4. 收藏、目标岗位、用户技能等用户侧记录采用恢复型 upsert，尽量保留旧值，只有显式字段才覆盖。

### 6.4 日志管理

已补充核心业务写操作日志，当前约定：

1. 查询接口不大量打日志。
2. service 层记录关键业务事件。
3. repository 层只在复杂写入或异常分支记录必要日志。
4. 日志不记录密码、token、完整请求体、答案正文、备注等敏感或大文本。
5. 日志事件要能定位模块、用户、资源和结果。

### 6.5 测试重点

当前已有 unit、api contract、integration 测试目录。测试重点不是追求覆盖率数字，而是约束业务流程：

1. 用户数据隔离。
2. 软删除/归档默认不可见。
3. 恢复型 upsert 不重复建记录。
4. RawJobRecord 重复消费安全。
5. 学习任务生成幂等复用。
6. 作答/跳过后进度正确更新。
7. 任务完成或归档后不能继续作答。
8. 错误请求不能产生部分写入。
9. 查询参数边界稳定。

## 7. 当前仍需注意的问题

1. **README 已把 RabbitMQ 写成下一轮目标，但当前代码默认 broker 仍是 Redis。** 如果切到 RabbitMQ，需要同步更新 `Settings`、`.env`、Docker Compose、Worker 启动命令和测试环境。
2. **Celery 现在只有骨架。** `debug.ping` 只能证明 worker app 可加载，不能证明岗位导入、技能同步、失败重试已经完成。
3. **不能继续只靠 seed 数据讲岗位摄入。** 下一阶段必须让爬虫或模拟爬虫通过 MQ 投递岗位消息，由 Worker 消费并调用 ingestion service。
4. **Worker 必须按重复消费安全设计。** MQ 可能重复投递，业务最终靠 `message_id / raw_content_hash / fingerprint` 和数据库唯一约束兜底。
5. **UserSession 是会话可信状态。** Redis refresh store 已有，但它不能替代可查询、可撤销、可审计的 `user_sessions`。
6. **技能匹配已经结构化。** 后续不要把技能匹配退回到对 JD 文本做大模型判断；当前主轴应继续使用 `skill_id + level`。
7. **学习任务生成幂等已经落地。** 后续重点不是再设计 `source_key`，而是把作答结果和用户技能评级策略接起来。
8. **Docker 部署还不是完整演示栈。** 当前 compose 没有 API、Worker、RabbitMQ；要演示闭环，需要补齐这些服务。

## 8. 对外描述口径

当前真实可描述为：

> JobPilot 是一个基于 FastAPI、PostgreSQL、Redis、SQLAlchemy 2.0 和 Alembic 的招聘岗位情报与求职准备后端。系统已经实现岗位 raw 数据摄入 service、字段规范化、fingerprint 去重、岗位搜索筛选、技能字典和岗位技能同步、用户收藏/目标岗位/技能画像、基于 `skill_id + level` 的技能覆盖分析，以及根据目标岗位技能缺口生成学习任务和记录作答进度。

下一阶段完成后，才适合描述为：

> 系统通过 UserSession 管理多设备登录会话，通过 Celery + RabbitMQ 解耦爬虫采集与岗位导入，通过 Worker 自动完成 RawJobRecord 入库、岗位 upsert、技能同步、失败重试和重复消费幂等处理，并将作答结果反馈到用户技能评级，形成“岗位导入 -> 技能匹配 -> 学习准备”的完整后端闭环。
