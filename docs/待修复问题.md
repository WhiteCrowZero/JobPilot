### P1-3：`False` 不能覆盖旧的 `True`，布尔字段可能变脏

**文件路径 / 函数**

* `src/job_pilot/modules/ingestion/repository.py`

    * `upsert_job_post_detail()`

**具体代码**

```python
"has_visa_sponsorship": case(
    (
        excluded.has_visa_sponsorship.is_(True),
        excluded.has_visa_sponsorship,
    ),
    else_=JobPostDetail.has_visa_sponsorship,
)
```

`has_relocation_support` 同理。

**为什么是问题**

如果第一次解析出 `has_visa_sponsorship=True`，后续来源明确解析出 `False`，当前代码不会覆盖旧值。

这会导致岗位详情长期显示旧的支持信息。

**建议修改方式**

建议把布尔字段改成三态语义：

```text
None = 未知
True = 明确支持
False = 明确不支持
```

upsert 时只在 excluded 不为 null 时覆盖：

```python
case(
    (excluded.has_visa_sponsorship.is_not(None), excluded.has_visa_sponsorship),
    else_=JobPostDetail.has_visa_sponsorship,
)
```

**修改风险**

中等。

需要确认 adapter 是否能区分“没有提到”和“明确不支持”。
**实际上大部分都是没有提到，默认没有提到，即为空**

### P2-4：API contract 测试偏少

**文件路径 / 函数**

* `tests/api/*`

**具体问题**

当前 API 测试主要覆盖 auth/current_user 和少量未授权/404。大量业务语义是在 service/application 层测的。

**为什么是问题**

service 测试能保证业务，但不能保证：

* query 参数解析
* list 参数解析
* enum 参数校验
* 422 响应
* HTTP status code
* router prefix 是否正确

**当前 MVP 是否可以接受**

当前可以保留，后续在 API 合同稳定阶段处理。

**建议修改方式**

优先补少量高价值 API 测试：

```text
GET /api/v1/jobs/search?skill_ids=1&skill_ids=2
GET /api/v1/jobs/search salary_min > salary_max -> 422
POST /api/v1/jobs/collections duplicate folder name -> 409
GET /api/v1/jobs/match/jobs/{id}/coverage unauthorized -> 401
```

**修改风险**

低。

### P2-5：测试环境依赖组织可以再拆

**文件路径 / 函数**

* `tests/conftest.py`
* `src/job_pilot/core/resources.py`

**具体问题**

我尝试跑 unit tests 时，加载 root `conftest.py` 就触发了：

```python
from job_pilot.core.resources import AppResources, build_app_resources
```

而 `core/resources.py` 顶层 import：

```python
from redis.asyncio import Redis
```

当前环境缺 `redis` 包时，unit tests 直接无法加载。

**为什么是问题**

unit test 最好尽可能少依赖完整 app resources。虽然你的正式依赖里有 redis，但测试结构上还是偏重。

**建议修改方式**

把 unit tests 的 fixture 和 app integration fixture 分开：

```text
tests/unit/conftest.py
tests/integration/conftest.py
tests/api/conftest.py
```

避免 unit test 导入完整 `build_app_resources()`。

**修改风险**

中等。

会动测试 fixture 结构，建议后面统一整理。

### P1-5：schema / contract 边界混在一起

**文件路径 / 函数**

多处，例如：

* `src/job_pilot/application.py`
* `src/job_pilot/modules/auth/service.py`
* `src/job_pilot/modules/job_posts/repository.py`
* `src/job_pilot/modules/job_collections/repository.py`
* `src/job_pilot/modules/user_skills/repository.py`
* `src/job_pilot/modules/job_targets/repository.py`

**具体代码**

repository 直接依赖 Pydantic schema，例如：

```python
from job_pilot.modules.job_posts.schemas import JobPostSearchParams
```

service 直接接收 HTTP schema，例如：

```python
payload: EmailRegisterRequest
payload: JobCollectionCreate
params: JobPostSearchParams
```

**为什么是问题**

现在 schema 同时承担了：

* HTTP request/response contract
* service command/query 参数
* repository filter 参数

这会导致：

* HTTP 参数变化影响 service/repository；
* worker/CLI 调用也被迫构造 Pydantic HTTP schema；
* 后续测试和内部 API 复用变重。

**当前 MVP 是否可以接受**

当前可以保留，后续在 worker/库化 API 稳定阶段处理。

**建议修改方式**

不用一下子搞 DDD。只需要逐步加轻量 contract：

```text
modules/job_posts/contracts.py
  JobPostSearchQuery

modules/job_collections/contracts.py
  CollectionListQuery
```

router 层负责：

```text
Pydantic schema -> contract dataclass
```

service/repository 接收 contract 或 primitives。

**修改风险**

中等。

涉及函数签名较多，建议分模块逐步改，不要一次性全项目重构。
